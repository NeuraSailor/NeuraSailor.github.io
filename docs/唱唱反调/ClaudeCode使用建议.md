# 🔮 Claude Code 高效使用建议：别让 AI 变成人工智障

> **作者**：NeuraSailor × ClaudeCode

Claude Code 是我每天用得最多的工具，但用得好和用不好之间，效率差距巨大。这篇文章不是"Claude Code 能做什么"——而是**怎么用才能不踩坑**。

---

## 1. 按任务难度调整 Model 与 Effort —— 复杂任务开 Ultracode

Claude Code 默认的模型和推理力度适合日常小任务，但**任务越复杂，配置越不能省**。

### 基本对应关系

| 任务类型                       | 推荐配置                             | 说明                          |
| ------------------------------ | ------------------------------------ | ----------------------------- |
| 修 typo、改一行配置、简单问答  | 默认即可                             | 杀鸡不用牛刀                  |
| 写一个新功能、重构一个模块     | `--model opus` + `--effort high` | 逻辑推理密集型                |
| 多文件联动、复杂架构、代码审查 | **开 Ultracode 工作流**        | 多 Agent 并行，质量碾压单线程 |

### Ultracode 是什么

Ultracode 是 Claude Code 的**多 Agent 工作流模式**。一句话解释：它不是让一个 AI 从头干到尾，而是**派多个 AI Agent 分工协作**——有的负责搜索和理解代码，有的负责设计方案，有的负责写代码，有的负责审查。

实际体感差距很大：

- **普通模式**处理复杂任务：像个实习生，能做但容易漏东西，你需要反复纠正。
- **Ultracode 模式**：像个 senior 带一个小团队，各司其职，互相验证，输出质量高一个档次。

直接用 `claude --ultracode` 启动，或者在会话中输入 `/ultracode` 切换。

### 一个简单的判断标准

如果你要说的需求需要**超过三句话才能描述清楚**，那就至少开到 `--effort high`。如果需求涉及**三个以上文件的联动修改**，直接开 Ultracode。省这个配置的时间，后面返工的代价更大。

## 2. 5 轮以上对话必须 Compact —— 否则降智明显

### 为什么会降智

Claude Code 每次对话，都会把历史消息作为上下文发给模型。**对话轮数越多，上下文越长，模型的注意力越分散。** 就像一个学生听了一小时课后开始走神——后面的回答质量明显下降。

具体表现：

- 开始"忘记"你前面说过的话
- 修改代码时漏掉关键约束
- 同一个问题反复出现，你纠正了又犯
- 回答变得啰嗦但抓不住重点
- 输出风格和前面不一致

### 怎么判断该 Compact 了

经验法则是 **5 轮对话**。这是我自己反复测试出来的阈值：

- 1-3 轮：模型注意力集中，质量最高。
- 4-5 轮：还行，但偶尔会有小纰漏。
- 6 轮以上：**降智明显**。你需要把同一句话重复两遍，模型才开始听话。

复杂任务（比如多文件修改）时，这个阈值可能更早——**3-4 轮就该 Compact**。

### 怎么操作

在 Claude Code 中输入 `/compact`，它会**把你的历史对话压缩成一份摘要，释放上下文空间**。模型就像休息了一下，重新集中注意力。

养成的习惯应该是：**做完一个阶段后，先 Compact 再进入下一个阶段。** 不要一口气聊 20 轮然后纳闷为什么 AI 越聊越蠢。

## 3. 稍微复杂的项目必须先 Plan —— 不留不确定性的配置

很多人打开 Claude Code 就开始提需求，想到哪说到哪。这在简单任务上行得通，但**稍微复杂一点的项目，不先 Plan 就是在给自己挖坑**。

### 为什么必须 Plan

AI 也是人（类比意义上）。你给它一个模糊的需求，它会**自动填充你不说的部分**——而且填充的很可能是错的。

比如你说"给我写一个用户登录功能"：

- 用 JWT 还是 Session？（它不会问你，直接选一个）
- Token 存哪里？localStorage 还是 cookie？（同上）
- 密码加密用什么算法？（同上）
- 错误处理怎么做？（同上）

它每做一次这样的猜测，就引入一次返工的可能。Plan 模式的价值就在于：**把 AI 的猜测变成你的确认。**

### Plan 模式怎么用

在 Claude Code 中，有两种方式：

1. **手动 Plan**：先说"我先 Plan 一下，别写代码"，让 AI 设计完方案后给你 review。确认无误了再说"开始写"。
2. **Plan Mode**：输入 `/plan` 进入 Plan Mode。AI 只做方案设计，不碰代码。方案确认后再切回执行模式。

Plan 的结果应该包含：

- 明确的实现步骤（第一步改什么，第二步加什么……）
- 关键的技术选择（用什么库、什么模式）
- 可能的风险点（哪里容易出 bug，哪里需要特别注意）

**没有 Plan，不写第一行代码。** 这个习惯帮我省了至少一半的返工时间。

## 4. 必须用 Git 管理 —— 一次改不对就回退重做

这是血的教训。

### 场景还原

AI 改代码改了一半，你发现方向不对。你想"就两个文件，手动改回来就行"——然后改漏了一处，花了一个小时 debug 才发现是之前残留的代码在作祟。

或者更糟：AI 连续改了十几个文件，你想回退，但没有 commit……那就只能一个个文件检查差异。

### 铁律

**每次让 Claude Code 做实质性修改之前，先 commit。** 无论是你手动写的还是 AI 改的，都要有个清晰的回退点。

具体做法：

1. 开始一个任务前：`git add -A && git commit -m "checkpoint: 开始做 XXX"`
2. AI 改完一轮，验证没问题：`git add -A && git commit -m "完成: XXX 功能"`
3. **如果 AI 改出问题了**：不要手动修修补补，直接 `git reset --hard HEAD~1` 回退，然后**换一种方式重新描述需求**。

### 为什么要回退而不是修

AI 改代码是一气呵成的——它的修改是连贯的思路。如果你发现方向不对，说明整个思路偏了。这时候修补，相当于在一张画歪了的素描上继续画——越描越歪。

回退重来有几个好处：

- 上下文干净，AI 不会受之前的错误方向影响
- 你可以重新组织需求描述，这次更精确
- 通常第二次比你想象中快得多——因为你在第一次试错中已经看清了问题

### Git 的另一个作用

版本控制还能帮你看到 AI 到底改了哪些东西。有时候 AI 会"顺手"改一些你没要求的文件，**git diff 能帮你一眼发现这些多余的操作。**

## 📋 四条规则的检查清单

每次打开 Claude Code 做正事之前，心里过一遍：

1. ☐ 这个任务什么难度？需要调 model/effort 或开 Ultracode 吗？
2. ☐ 聊到第几轮了？是不是该 Compact 了？
3. ☐ 这个需求够复杂吗？需要先 Plan 再动手吗？
4. ☐ 改之前 commit 了吗？出问题能一键回退吗？

这四条规则本身不复杂，但坚持做到每一条，就是从**"AI 在帮我干活"**到**"AI 在高效地帮我干活"**的差距。
